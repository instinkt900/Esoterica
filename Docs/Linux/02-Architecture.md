# Target Architecture

How the Linux port fits into the existing engine. Read this before you design any part of it.

---

## Build system

### Decision: extend `Code/Scripts/NinjaGen/NinjaGen.py`. Not CMake.

**Why.** The `.vcxproj` files list every source file explicitly. `Esoterica.Base` has 147
`ClCompile` entries, `Esoterica.Engine.Runtime` has 236, and `Esoterica.Engine.Tools` has 155.
None of them has an `ExcludedFromBuild` entry. A generator that derives its file list from the
`.vcxproj` files therefore picks up upstream source additions, removals, and moves
*automatically, with no Linux-side change*.

A parallel CMake tree would need a manual sync against those file lists on every upstream merge.
Over the life of this fork that is the dominant maintenance cost, and it is exactly the cost
this project works to avoid.

Two trade-offs come with the decision: an in-house build tool, and weaker system-library
discovery than CMake's `find_package`. `pkg-config` covers the handful of system libraries
involved, which limits the second. See [03-Dependencies.md](03-Dependencies.md).

### Why not the C++ `BuildGenerator` app

`Code/Applications/BuildGenerator/BuildGeneratorApplication.cpp` is vestigial. It emits `.obj`
rule *references* with no rule definitions, no link steps, no include directories, and no
preprocessor defines. It also parses the legacy `.sln` GUID format
(`{8BC9CEB8-8B4A-11D0-8D11-00A0C91BC942}`), so it is already broken against the repo's current
`Esoterica.slnx`. There is nothing to build on. Leave it alone, and do not delete it
(Conventions rule 3).

### What the generator must do

Input: `Esoterica.slnx`, the `.vcxproj` files it references, and the `.props` sheets each
project imports.

Output: `Build/Linux/Esoterica.ninja` and `compile_commands.json`.

```
Esoterica.slnx  ──parse XML──►  project list
      │
      └─► for each .vcxproj:
              ClCompile Include=...        ──►  source list  (filter by platform suffix)
              ClInclude Include=...        ──►  header list  (for the REFLECT rule's deps)
              ProjectReference Include=... ──►  dependency edges
              ConfigurationType            ──►  .so / .a / executable
              <Import Project="...props">  ──►  which external deps to link
      │
      └─► _Module/_Autogenerated/*.cpp     ──►  globbed, not listed in the vcxproj
```

The behavior it needs, in rough priority order:

1. **`.slnx` XML parsing.** The current file is XML, with `<Project Path="..." Id="..."/>`
   elements. It is much simpler than the old format. Honor the `<Build Project="false"/>` and
   `<Build Solution="Shipping|*" Project="false"/>` exclusions.
2. **Platform-suffix filtering.** Exclude `*_Win32.cpp`. Include the `*_Linux.cpp` files found
   on disk next to them. Upstream's `.vcxproj` will never list the `_Linux.cpp` files, so the
   generator must find them by globbing the same directory. **Warn loudly on any
   `_<Platform>.cpp` suffix it does not recognize**, so that a new upstream platform cannot
   disappear silently.
3. **Autogenerated source globbing.** `_Module/_Autogenerated/TypeInfo/*.cpp` and
   `_Module/_Autogenerated/Shaders/*.cpp` are wildcards in MSBuild (`Esoterica.props`,
   `_WildCardClCompile`). Glob them here too.
4. **Per-project defines.** `Esoterica.props` sets
   `$(ProjectName.ToUpper().Replace('.','_'))`, so `Esoterica.Base` gets `-DESOTERICA_BASE`.
   This drives the `dllexport` and `dllimport` switch in every `_Module/API.h`. Reproduce it
   exactly.
5. **Configuration defines.** `-DEE_DEBUG=1`, `-DEE_RELEASE=1`, or `-DEE_SHIPPING=1`. Add
   `-DEE_DLL` for Debug and Release only, because Shipping links statically. Add
   `-D_HAS_EXCEPTIONS=0` and `-fno-exceptions`.
6. **`ConfigurationType` varies per configuration.** `Esoterica.Base` is `DynamicLibrary` in
   Debug and Release, and `StaticLibrary` in Shipping. Read it per config, not once per
   project.
7. **Library linking.** Map each imported `.props` sheet to its Linux link flags.
   [03-Dependencies.md](03-Dependencies.md) holds the table.
8. **Shared object output and `rpath`.** `.so` outputs need `-fPIC`. Executables need
   `-Wl,-rpath,'$ORIGIN'` so they find sibling `.so` files. This replaces MSBuild's DLL-copy
   targets, such as `DXC_CopyDLL` in `DXC.props`.
9. **`compile_commands.json`** for clangd. The upstream version already does this with
   `ninja -t compdb`. Keep it, but generate it from the real Linux toolchain instead of
   `clang-cl`.

### Bugs to fix in the existing `NinjaGen.py`

Each of these comes from the stale version, and each is a real defect:

- It parses `Esoterica.sln`, which no longer exists. It needs `.slnx`.
- `cpp_rule` calls `toolchain.compiler_c` instead of `compiler_cpp`.
- `-fsanitize-address` should be `-fsanitize=address`.
- It does no library linking at all. There is not one `-l` flag.
- It sets no per-project preprocessor defines, so the `dllexport` and `dllimport` switch is
  broken.
- Object paths embed full source paths, which breaks on absolute paths.
- Hardcoded include flags duplicate what the `.props` sheets already declare.
- `-D__LINUX__` should go. Use the compiler-provided `__linux__`.
- It sets `-std=c++17`. The project needs C++20 (`Esoterica.props` sets `stdcpp20`).
- The `WineGCC` toolchain is a dead end for this port. Drop it.

### Configurations and output layout

Mirror the MSBuild layout, so that habits and tooling carry over:

```
Build/Linux_Debug/        Build/Linux_Release/        Build/Linux_Shipping/
Build/_Temp/Linux_<Config>/<ProjectName>/            <- object files
```

Keep the ASan, TSan, and UBSan variants that the stale script had. They are useful on Linux and
almost free to generate. Drop MSan. It needs an instrumented libc++ to be useful, and without
one it produces mostly false positives.

> **Gotcha:** `.gitignore` contains lowercase `build/`. Linux filesystems are case-sensitive,
> so git does **not** ignore `Build/`. Add `Build/` to `.gitignore` during Phase 0. This is an
> upstream edit, so record it in the registry.

## Platform abstraction layer

The engine's existing convention is already the right shape. Follow it exactly.

```
Code/Base/<System>/<System>.h                       shared interface
Code/Base/<System>/Platform/<System>_Win32.cpp      Windows implementation
Code/Base/<System>/Platform/<System>_Linux.cpp      Linux implementation   <- new
```

The interface headers are already platform-neutral, and the pattern goes further than a quick
survey suggests. Two examples show the intended style:

**Constants defined in the platform translation unit.** `FileSystemPath.h:23` declares
`static char const s_pathDelimiter;`, deliberately not `constexpr`.
`FileSystemPath_Win32.cpp:9` defines it as `'\\'`. The Linux file defines it as `'/'`, and **no
shared code changes at all**. `FileSystemPath.cpp` already uses the symbol abstractly in about
20 places.

**Opaque native handles.** `Threading::SyncEvent` holds a `void* m_pNativeHandle`.
`Platform::GetMainWindowHandle()` returns `void*`. `RHI::SwapchainParameters` holds
`void* m_pNativeWindowHandle`. No shared header names a platform type.

Where you need a platform-specific *helper* namespace, mirror `EE::Platform::Win32` as
`EE::Platform::Linux`. About 30 call sites reference `Platform::Win32::` directly. Most are
`GetLastErrorMessage()` inside other `_Win32.cpp` files, which is fine. The rest are
`OpenInExplorer` from 6 EngineTools call sites, and `GetCurrentModulePath`, `StartProcess`, and
`KillProcess` from `BaseModule.cpp`. [TouchedFiles.md](TouchedFiles.md) lists those
cross-platform call sites, and Phases 1 and 7 handle them.

### From `dllexport` to visibility

`Code/Base/_Module/API.h`, and its per-module siblings, do this:

```cpp
#if EE_DLL
    #if ESOTERICA_BASE
        #define EE_BASE_API __declspec(dllexport)
    #else
        #define EE_BASE_API __declspec(dllimport)
    #endif
#else
    #define EE_BASE_API
#endif
```

On Linux the export case becomes `__attribute__(( visibility( "default" ) ))`, and the import
case becomes nothing. There is one such header per module: `Base`, `Engine`, `EngineTools`,
`Game`, and `GameTools`. Each takes the same `#elif` treatment. Compile the `.so` targets with
`-fvisibility=hidden` so the attribute means something.

## Renderer

### The abstraction is sound

`Code/Base/Render/RHI.h` is a flat, C-style, free-function API of about 110 functions in
namespace `EE::Render::RHI`. It contains **no** `ID3D12*`, `DXGI*`, or `D3D12_*` identifiers.
Every opaque type (`Context`, `Queue`, `Buffer`, `Texture`, `Sampler`, `Shader`,
`RootSignature`, `Pipeline`, `Swapchain`, `CommandBuffer`, and the rest) is a forward-declared
struct that only the backend translation unit defines.

The Vulkan backend is therefore a **new sibling file**, `Code/Base/Render/RHI_Vulkan.cpp`. The
only shared-file change is the build generator choosing which one to compile. This plan does
not refactor `RHI.h`, and it should not.

```
Code/Base/Render/RHI.h                  shared, unchanged
Code/Base/Render/RHI_Direct3D12.cpp     6,084 lines, Windows only
Code/Base/Render/RHI_Vulkan.cpp         new, Linux (and later, optionally, Windows)
```

`RHI_Direct3D12.cpp` is the reference implementation for every function. Read it before you
write the Vulkan equivalent. It encodes the intended semantics, and its comments explain the
contracts that are not obvious.

### Vulkan requirements for parity

The API surface implies these features. Full parity is the goal, so all of them are in scope.

| `RHI.h` concept | Vulkan requirement |
|---|---|
| Shader Model 6.6 bindless, `CmdSetRootParameter` | `VK_EXT_descriptor_indexing` (core 1.2), `VK_KHR_buffer_device_address` (core 1.2) |
| `CmdSetRenderTargets` with load and store actions | `VK_KHR_dynamic_rendering` (core 1.3) |
| `CmdDispatchRays`, `CmdBuildAccelerationStructure` | `VK_KHR_ray_tracing_pipeline`, `VK_KHR_acceleration_structure`, `VK_KHR_deferred_host_operations` |
| `CmdDispatchMesh` | `VK_EXT_mesh_shader` |
| `CmdSetShadingRate`, `ShadingRateCombiner` | `VK_KHR_fragment_shading_rate` |
| `CmdExecuteIndirect`, `CommandSignature` | `VK_KHR_draw_indirect_count` (core 1.2), plus a compute pre-pass for the multi-argument cases |
| `SetDebugName` (9 overloads), debug markers | `VK_EXT_debug_utils` |
| `RootSignature`, `RootConstants` | `VkPipelineLayout` and push constants |
| `BeginFrameCapture` and `EndFrameCapture` | RenderDoc in-application API (`librenderdoc.so`) |
| `D3D12MemoryAllocator` | VulkanMemoryAllocator (VMA) |
| `WaveOpsSupportFlags` | `VK_KHR_shader_subgroup_*` (core 1.1 and 1.2) |

The baseline is **Vulkan 1.3**. It makes dynamic rendering, descriptor indexing, buffer device
address, timeline semaphores, and synchronization2 core features, which removes a lot of
extension plumbing.

Note `QueueGetCurrentSemaphore`, `QueueGetCompletedSemaphore`, `QueueHostWait`, and
`QueueDeviceWait`. This is a monotonic-counter model. It maps directly onto **timeline
semaphores** (`VK_KHR_timeline_semaphore`, core 1.2), not onto binary semaphores. Getting this
mapping right early decides whether the rest of the backend stays clean.

### Shader pipeline

```
.esh  ──Reflector──►  HLSL  ──DXC──►  bytecode  ──reflection──►  generated .cpp
```

On Windows, DXC produces DXIL, and `ID3D12ShaderReflection` (`d3d12shader.h`) reflects it. On
Linux, DXC produces SPIR-V with `-spirv`, and **SPIRV-Reflect** reflects it.

DXC builds and runs on Linux, so the HLSL front end does not change and the 26 `.esh` files need
no edits. The reflection layer is the part to replace.
`Code/Applications/Reflector/ShaderReflection/` is about 1,900 lines, and the D3D dependency
sits only in `ShaderReflection_ShaderCompiler.{h,cpp}`. See
[Phase 4](Phases/Phase4-ShaderPipeline.md).

## Application and entry points

`Win32Application` (`Application_Win32.h`) is a base class whose virtual interface is *almost*
platform-neutral. `Initialize`, `Shutdown`, `ApplicationLoop`, `ResizeMainWindow`,
`OnUserExitRequest`, `ReadWindowSettings`, and `WriteWindowSettings` are all fine. But it leaks
Win32 types through:

- the constructor, which takes `HINSTANCE`
- `virtual LRESULT WindowMessageProcessor( HWND, UINT, WPARAM, LPARAM )`
- `virtual void ProcessInputMessage( UINT, WPARAM, LPARAM )`
- `HICON GetIcon() const`
- `LRESULT BorderlessWindowHitTest( POINT )`

Linux therefore gets a sibling `LinuxApplication` class built on SDL3, plus sibling app
subclasses. The duplication is small, because the app subclasses are thin.
`EditorApplication_Win32.cpp` is 127 lines and `EngineApplication_Win32.cpp` is 124. The real
editor logic lives in the platform-neutral `Code/Applications/Editor/EditorUI.cpp`.

```
Code/Base/Application/Platform/Application_Linux.{h,cpp}     LinuxApplication
Code/Applications/Editor/Linux/EditorApplication_Linux.{h,cpp}
Code/Applications/Engine/Linux/EngineApplication_Linux.{h,cpp}
Code/Applications/ResourceServer/...                          (see Phase 7)
```

`_tWinMain` becomes `int main( int argc, char** argv )`. Four applications already use plain
`main`: `Reflector`, `ResourceCompiler`, `BuildGenerator`, and `Tester`. That is why Phases 2
and 3 can land before any windowing work exists.

Do **not** try to unify `Win32Application` and `LinuxApplication` under a common base by
refactoring the Win32 class. That is a large edit to an upstream file for a cosmetic gain, and
it breaks Conventions rule 2.

## Dependency graph and phase ordering

```
Base ──► Engine ──► Game
  │        │
  │        └──► EngineTools ──► GameTools
  │                 │
  └──► Reflector    ├──► ResourceCompiler
                    ├──► ResourceServer
                    ├──► Editor
                    └──► Engine (app)
```

Nothing compiles until the Reflector has generated `_Module/_Autogenerated/`. That is why Phase
2 comes before Phase 3, even though both are console applications. Only the `Engine` and
`Editor` applications need the renderer, which is why Phases 2 to 4 can finish with no Vulkan
code at all.
