# Phase 4 - Shader Pipeline

**Goal:** `.esh` shaders compile to SPIR-V on Linux, with reflection data generated for the
engine.

**Deliverable:** `./CompileShaders.sh` runs the Reflector's shader path and fills
`_Module/_Autogenerated/Shaders/`.

**Prerequisites:** Phases 1, 2, and 3 complete.

**Rough cost:** 2-4 weeks.

**Read first:** [00-Conventions.md](../00-Conventions.md),
[02-Architecture.md, Shader pipeline](../02-Architecture.md#shader-pipeline),
[Phase2-Reflector.md](Phase2-Reflector.md), because this phase reverses its P2.3.

---

## Why this comes before the Vulkan backend

The Vulkan backend consumes SPIR-V and reflection metadata. If you build it before the shader
pipeline exists, Phase 5 starts with nothing to feed it, and every bring-up step waits on
hand-written test shaders. Land the pipeline first, and Phase 5 has real content from day one.

## The shape of the problem

```
.esh  ──Reflector parse──►  HLSL  ──DXC──►  bytecode  ──reflect──►  generated .cpp
```

On Windows, DXC produces **DXIL**, and `ID3D12ShaderReflection` from `d3d12shader.h` reflects
it. On Linux, DXC produces **SPIR-V** with `-spirv`, and **SPIRV-Reflect** reflects it.

The good news: **DXC builds and runs on Linux.** The HLSL front end does not change, and **none
of the 26 `.esh` files need edits.** The work stays inside the reflection layer.

`Code/Applications/Reflector/ShaderReflection/` is about 1,900 lines across four pairs:

| File | LOC | Platform coupling |
|---|---|---|
| `ShaderReflection_ShaderParser.{h,cpp}` | 518 | none, it parses `.esh` |
| `ShaderReflection_ShaderCompiler.{h,cpp}` | 485 | **all of it**, through `d3d12shader.h` and `dxcapi.h` |
| `ShaderReflection_ShaderInputReflector.{h,cpp}` | 340 | probably some, it consumes reflection results |
| `ShaderReflection_CodeGenerator.{h,cpp}` | 563 | none, it emits C++ |

The parser and the code generator are portable as they stand. The compiler is the port. The
input reflector is the boundary to inspect.

## Tasks

### P4.1 - Build DXC for Linux

Add a `dxc` target to `DownloadDependencies.sh` that produces
`External/DirectXShaderCompiler/{inc,lib}/` and `libdxcompiler.so`.

Notes:

- DXC's `dxcapi.h` exists on Linux, and it uses a COM-lite shim that DXC provides, with
  `IUnknown` and `CComPtr` equivalents. The API shape is the same. The ABI details differ.
- **DXIL signing (`dxil.dll`) is Windows-only and does not matter here.** SPIR-V is not signed.
  The `DXC.props` `Copy` target that stages `dxil.dll` has no Linux equivalent.
- Pin the version, and record it in [03-Dependencies.md](../03-Dependencies.md).
- Expect a long build. Put it after the cheap dependencies in the script.

Reverse the Phase 2 P2.3 exclusion here. Re-enable the `ShaderReflection/` sources for Linux in
the build generator, and remove whatever guard or define P2.3 added. [Progress.md](../Progress.md)
records exactly what P2.3 did.

### P4.2 - Get SPIRV-Reflect - **moved to Phase 5**

**Nothing in Phase 4 consumes SPIRV-Reflect.** The only code that reflects compiled shader
bytecode is `RHI_Direct3D12.cpp:1007-1096`, building root signature and descriptor information at
runtime. Its Vulkan sibling is what needs SPIRV-Reflect, so this is a Phase 5 dependency.
Vendoring it here would pin a library with no caller. See the 2026-08-28 entry in
[Progress.md](../Progress.md), and P4.4 below for how this was found.

The task text is kept below, unchanged, for whoever does it in Phase 5.

#### Original text

Vendor it into `External/SPIRV-Reflect/`, not `Code/**/ThirdParty/`. See Conventions rule 5. It
is one `.c` and `.h` pair, plus headers. Pin the version.

Add it to the build generator's dependency mapping.

### P4.3 - Emit SPIR-V from DXC

In `ShaderReflection_ShaderCompiler.cpp`, the Linux path passes `-spirv` to DXC, along with the
Vulkan-targeting flags. What matters:

- **`-fvk-use-dx-layout`**, or its equivalent, keeps constant buffer layout consistent with the
  Direct3D path. A layout mismatch between the two backends produces silently wrong rendering,
  which costs a great deal to debug in Phase 5. Get this right now.
- **Bindless and descriptor indexing.** The engine targets Shader Model 6.6 with a bindless
  model. DXC's SPIR-V backend maps SM6.6 resource descriptor heaps onto Vulkan descriptor
  indexing, but the mapping is not automatic. Investigate `-fvk-bind-resource-heap`,
  `-fvk-bind-sampler-heap`, and the `SPV_EXT_descriptor_indexing` output. Decide the binding
  model **together with Phase 5**, because the RHI's `CmdSetRootParameter` implementation must
  agree with what the shaders were compiled to expect. Record the decision in
  [Progress.md](../Progress.md). It is the most consequential decision in this phase.
- **`-fvk-invert-y`**, if the engine assumes Direct3D's clip-space Y direction. Read the viewport
  setup in `RHI_Direct3D12.cpp` and the engine's projection matrices, and decide whether the
  inversion belongs here or in the Vulkan backend's viewport. Pick one place. Doing it in both,
  or in neither, is the classic Vulkan porting bug.
- **Shader stage mapping** for `RHI::ShaderStage`, including the mesh, amplification, and
  raytracing stages, because parity is the goal.

### P4.4 - Replace `ID3D12ShaderReflection` with SPIRV-Reflect - **not applicable**

**There is nothing to replace.** This task rests on a premise that is not true of this codebase,
checked on 2026-08-28 before starting it:

- Every use of `ID3D12ShaderReflection` is in `RHI_Direct3D12.cpp`, which is excluded from the
  Linux build and belongs to Phase 5. The Reflector only *includes* `d3d12shader.h` and never
  calls it, which `ShaderReflection_ShaderCompiler.h:10` already says.
- `ShaderCompiler` exposes no reflection results. `ReflectedShader` is platform-neutral.
- `m_parameters` and `m_resourceTable` are filled by `ShaderReflection_ShaderParser.cpp` parsing
  the `.esh` **source text**, not by any reflection API.

The platform-neutral structure this task asks for already exists, and is called
`ReflectedShader`. No new abstraction is needed, and none should be added. See the 2026-08-28
entry in [Progress.md](../Progress.md).

The task text is kept below, unchanged, because the semantic mismatch table is still useful
reference for the Phase 5 backend, which does reflect bytecode.

#### Original text

`ShaderReflection_ShaderCompiler.h` currently exposes reflection results
in D3D terms, and `ShaderReflection_ShaderInputReflector.cpp` consumes them.

The approach:

1. Read `ShaderReflection_ShaderInputReflector.{h,cpp}` and
   `ShaderReflection_CodeGenerator.cpp` to find **exactly which reflection facts the generated
   code needs**: binding indices, register spaces, resource types, constant buffer members and
   offsets, thread group sizes, and input and output signatures.
2. Define that set as a platform-neutral intermediate structure.
3. Fill it from `ID3D12ShaderReflection` on Windows, and from SPIRV-Reflect on Linux.

**This is the one place in the port where a new abstraction is the right call**, because the
alternative is duplicating the reflector's downstream logic. Keep the abstraction inside
`ShaderReflection_*`. Do not let it leak into `RHI.h` or the engine.

The cleanest implementation will probably need to restructure the public interface of
`ShaderReflection_ShaderCompiler.h`. That is a bigger upstream edit than this plan's usual 2-line
rule. **It is acceptable here, but record it clearly in
[TouchedFiles.md](../TouchedFiles.md)** as a real edit, and keep the change as small as you can.
Prefer adding a parallel Linux code path over rewriting the Windows one.

Watch for semantic mismatches between the two reflection APIs:

| Concept | D3D12 | SPIR-V |
|---|---|---|
| Register and space | `BindPoint`, `Space` | `binding`, `descriptor_set` |
| CBuffer layout | explicit offsets from reflection | offsets are present, but they depend on the layout rules |
| Resource type | `D3D_SHADER_INPUT_TYPE` | `SpvReflectDescriptorType` |
| Arrays and unbounded arrays | `BindCount == 0` means unbounded | `array.dims`, or `0` for runtime arrays |
| Thread group size | `GetThreadGroupSize` | `SpvReflectEntryPoint::local_size` |

The unbounded-array case matters most, because the engine is bindless.

### P4.5 - `CompileShaders.sh`

Mirror `CompileShaders.bat`:

```bash
#!/usr/bin/env bash
set -euo pipefail
"Build/Linux_Release/EsotericaReflector" -s Esoterica.slnx -shaders -hotreload
```

Find out what `-hotreload` does on this path before you include it. It may assume a running
process to notify.

### P4.6 - Check the generated shader code

`ShaderReflection_CodeGenerator.cpp` generates `_Module/_Autogenerated/Shaders/*.cpp`, and the
engine compiles it in.

The generated code will legitimately **differ between platforms**, because it embeds bytecode and
SPIR-V is not DXIL. Unlike Phases 2 and 3, byte-identical output is *not* the goal here. Check
this instead:

1. The generated C++ compiles.
2. The **structure** matches: the same shader entries, the same binding tables, and the same
   constant buffer member names and sizes. Diff the generated files with the bytecode blobs
   ignored.
3. The binding indices agree with what the Phase 5 backend will expect.

Also confirm that the Phase 0 generator's glob of `_Module/_Autogenerated/Shaders/*.cpp` picks
these up. That is P0.4.

## Acceptance criteria

1. `libdxcompiler.so` builds, and the Reflector links against it.
2. `./CompileShaders.sh` exits 0 and fills `_Module/_Autogenerated/Shaders/` for `Base`
   (`RHI.esh`) and `Engine` (25 `.esh` files).
3. All 26 `.esh` files compile to valid SPIR-V. Check with `spirv-val`. Every module passes.
4. No `.esh` file is edited.
5. The generated `.cpp` files compile as part of `Esoterica.Base` and
   `Esoterica.Engine.Runtime`.
6. A structural diff against the Windows-generated output shows the same shader set, entry
   points, and binding tables. Only the bytecode differs.
7. Reflection output is correct for the bindless cases. Unbounded descriptor arrays are reported
   with the right set and binding, and flagged as runtime arrays.
8. The binding model decision from P4.3 is recorded in [Progress.md](../Progress.md), in enough
   detail for Phase 5 to implement against it.
9. The clip-space Y decision is recorded, and it names which layer performs the inversion.
10. **The Windows MSBuild build still succeeds**, the Windows Reflector still compiles shaders to
    DXIL, and its generated output is unchanged from before this phase.
11. Every upstream file you edited is in [TouchedFiles.md](../TouchedFiles.md) with status
    `done`.

Criterion 10 deserves emphasis. P4.4 restructures a file that the Windows build depends on.
Checking that the Windows DXIL output is *unchanged* is the only way to know you did not regress
it.

## Do not

- Edit any `.esh` file.
- Let the reflection abstraction leak into `RHI.h` or engine code.
- Decide the bindless binding model alone. It is a joint decision with Phase 5, and getting it
  wrong wastes weeks there.
- Apply Y-inversion in both the shader compiler and the Vulkan viewport.
- Vendor SPIRV-Reflect into `Code/**/ThirdParty/`.
