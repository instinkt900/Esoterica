# Phase 4 — Shader Pipeline

**Goal:** `.esh` shaders compile to SPIR-V on Linux, with reflection data generated for the
engine.

**Deliverable:** `./CompileShaders.sh` runs the Reflector's shader path and populates
`_Module/_Autogenerated/Shaders/`.

**Prerequisites:** Phases 1, 2, 3 complete.

**Rough cost:** 2–4 weeks.

**Read first:** [00-Conventions.md](../00-Conventions.md),
[02-Architecture.md § Shader pipeline](../02-Architecture.md#shader-pipeline),
[Phase2-Reflector.md](Phase2-Reflector.md) (this phase reverses its P2.3).

---

## Why before the Vulkan backend

The Vulkan backend consumes SPIR-V and reflection metadata. Building it before the shader
pipeline exists means Phase 5 starts with nothing to feed it, and every bring-up step is blocked
on hand-written test shaders. Land the pipeline first, and Phase 5 has real content from day one.

## The shape of the problem

```
.esh  ──Reflector parse──►  HLSL  ──DXC──►  bytecode  ──reflect──►  generated .cpp
```

Windows: DXC → **DXIL**, reflected via `ID3D12ShaderReflection` from `d3d12shader.h`.
Linux: DXC → **SPIR-V** (`-spirv`), reflected via **SPIRV-Reflect**.

The good news: **DXC builds and runs on Linux**, so the HLSL front end is unchanged and **none of
the 26 `.esh` files need editing.** The work is confined to the reflection layer.

`Code/Applications/Reflector/ShaderReflection/` is ~1,900 lines across four pairs:

| File | LOC | Platform coupling |
|---|---|---|
| `ShaderReflection_ShaderParser.{h,cpp}` | 518 | none — parses `.esh` |
| `ShaderReflection_ShaderCompiler.{h,cpp}` | 485 | **all of it** — `d3d12shader.h`, `dxcapi.h` |
| `ShaderReflection_ShaderInputReflector.{h,cpp}` | 340 | likely some — consumes reflection results |
| `ShaderReflection_CodeGenerator.{h,cpp}` | 563 | none — emits C++ |

So the parser and code generator are portable as-is. The compiler is the port, and the input
reflector is the boundary that needs inspecting.

## Tasks

### P4.1 — Build DXC for Linux

Extend `DownloadDependencies.sh` with a `dxc` target producing
`External/DirectXShaderCompiler/{inc,lib}/` and `libdxcompiler.so`.

Notes:
- DXC's `dxcapi.h` is available on Linux and uses a COM-lite shim (`IUnknown`,
  `CComPtr` equivalents) that DXC provides. The API shape is the same; the ABI details differ.
- **DXIL signing (`dxil.dll`) is Windows-only and irrelevant here** — SPIR-V is not signed. The
  `DXC.props` `Copy` target that stages `dxil.dll` has no Linux equivalent.
- Pin the version. Record it in [03-Dependencies.md](../03-Dependencies.md).
- Expect a long build; sequence it after the cheap dependencies in the script.

Reverse Phase 2's P2.3 exclusion here — re-enable the `ShaderReflection/` sources for Linux in
the build generator, and remove whatever guard or define P2.3 introduced. Read
[Progress.md](../Progress.md) for exactly what P2.3 did.

### P4.2 — Acquire SPIRV-Reflect

Vendor into `External/SPIRV-Reflect/` (not `Code/**/ThirdParty/` — Conventions rule 5). It is a
single `.c`/`.h` pair plus headers. Pin the version.

Add it to the build generator's dependency mapping.

### P4.3 — Emit SPIR-V from DXC

In `ShaderReflection_ShaderCompiler.cpp`, the Linux path passes `-spirv` to DXC along with the
Vulkan-targeting flags. Key considerations:

- **`-fvk-use-dx-layout`** or equivalent, to keep constant buffer layout consistent with the
  Direct3D path. Layout mismatches between the two backends produce silently wrong rendering,
  which is expensive to debug in Phase 5 — get this right now.
- **Bindless / descriptor indexing** — the engine targets Shader Model 6.6 with a bindless model.
  DXC's SPIR-V backend maps SM6.6 resource descriptor heaps onto Vulkan descriptor indexing, but
  the mapping is not automatic. Investigate `-fvk-bind-resource-heap`,
  `-fvk-bind-sampler-heap`, and the `SPV_EXT_descriptor_indexing` output, and decide the binding
  model **jointly with Phase 5** — the RHI's `CmdSetRootParameter` implementation must agree with
  whatever the shaders were compiled to expect. Record the decision in
  [Progress.md](../Progress.md); it is the single most consequential decision in this phase.
- **`-fvk-invert-y`** if the engine assumes Direct3D's clip-space Y direction. Determine from
  `RHI_Direct3D12.cpp`'s viewport setup and the engine's projection matrices whether inversion
  belongs here or in the Vulkan backend's viewport. Pick one place; doing it in both, or neither,
  is the classic Vulkan porting bug.
- Shader stage mapping for `RHI::ShaderStage`, including mesh/amplification and raytracing
  stages, since parity is the goal.

### P4.4 — Replace `ID3D12ShaderReflection` with SPIRV-Reflect

The substantive work. `ShaderReflection_ShaderCompiler.h` currently exposes reflection results in
D3D terms; the consumer is `ShaderReflection_ShaderInputReflector.cpp`.

Approach:

1. Read `ShaderReflection_ShaderInputReflector.{h,cpp}` and `ShaderReflection_CodeGenerator.cpp`
   to determine **exactly what reflection facts the generated code needs** — binding indices,
   register spaces, resource types, constant buffer members and offsets, thread group sizes,
   input/output signatures.
2. Define that set as a platform-neutral intermediate structure.
3. Populate it from `ID3D12ShaderReflection` on Windows and from SPIRV-Reflect on Linux.

**This is the one place in the port where introducing an abstraction is the right call**, because
the alternative is duplicating the reflector's downstream logic. But keep the abstraction inside
`ShaderReflection_*`; do not let it leak into `RHI.h` or the engine.

If the cleanest implementation requires restructuring
`ShaderReflection_ShaderCompiler.h`'s public interface — which is likely — that is a larger
upstream edit than this plan's usual 2-line rule. **That is acceptable here, but record it
prominently in [TouchedFiles.md](../TouchedFiles.md)** as a substantive edit, and keep the change
as surgical as you can. Prefer adding a parallel Linux code path over rewriting the Windows one.

Watch for semantic mismatches between the two reflection APIs:

| Concept | D3D12 | SPIR-V |
|---|---|---|
| Register + space | `BindPoint`, `Space` | `binding`, `descriptor_set` |
| CBuffer layout | explicit offsets from reflection | offsets present but layout-rule-dependent |
| Resource type | `D3D_SHADER_INPUT_TYPE` | `SpvReflectDescriptorType` |
| Arrays / unbounded | `BindCount == 0` for unbounded | `array.dims`, or `0` for runtime arrays |
| Thread group size | `GetThreadGroupSize` | `SpvReflectEntryPoint::local_size` |

The unbounded-array case matters specifically because the engine is bindless.

### P4.5 — `CompileShaders.sh`

Mirror `CompileShaders.bat`:

```bash
#!/usr/bin/env bash
set -euo pipefail
"Build/Linux_Release/EsotericaReflector" -s Esoterica.slnx -shaders -hotreload
```

Confirm what `-hotreload` does on this path before including it — it may assume a running
process to notify.

### P4.6 — Verify generated shader code

`_Module/_Autogenerated/Shaders/*.cpp` is generated by `ShaderReflection_CodeGenerator.cpp` and
compiled into the engine.

The generated code will legitimately **differ between platforms** — it embeds bytecode, and
SPIR-V is not DXIL. So unlike Phases 2 and 3, byte-identical output is *not* the goal here.
Instead verify:

1. The generated C++ compiles.
2. The **structure** matches — same shader entries, same binding tables, same constant buffer
   member names and sizes. Diff the generated files ignoring the bytecode blobs.
3. Binding indices agree with what the Phase 5 backend will expect.

Also confirm the Phase 0 generator's glob of `_Module/_Autogenerated/Shaders/*.cpp` picks these
up (P0.4).

## Acceptance criteria

1. `libdxcompiler.so` builds and the Reflector links against it.
2. `./CompileShaders.sh` exits 0 and populates `_Module/_Autogenerated/Shaders/` for `Base`
   (`RHI.esh`) and `Engine` (25 `.esh` files).
3. All 26 `.esh` files compile to valid SPIR-V. Validate with `spirv-val` — every module passes.
4. Zero edits to any `.esh` file.
5. The generated `.cpp` files compile as part of `Esoterica.Base` and
   `Esoterica.Engine.Runtime`.
6. Structural diff against the Windows-generated output shows the same shader set, entry points,
   and binding tables, with only bytecode differing.
7. Reflection output is correct for the bindless cases specifically — unbounded descriptor arrays
   are reported with the right set/binding and flagged as runtime arrays.
8. The binding model decision (P4.3) is recorded in [Progress.md](../Progress.md) in enough
   detail for Phase 5 to implement against it.
9. The clip-space Y convention decision is recorded, naming which layer performs the inversion.
10. **The Windows MSBuild build still succeeds**, the Windows Reflector still compiles shaders to
    DXIL, and its generated output is unchanged from before this phase.
11. Every upstream file edited is in [TouchedFiles.md](../TouchedFiles.md) with status `done`.

Criterion 10 deserves emphasis: P4.4 restructures a file the Windows build depends on. Verifying
that the Windows DXIL output is *unchanged* is the only way to know you did not regress it.

## Do not

- Edit any `.esh` file.
- Let the reflection abstraction leak into `RHI.h` or engine code.
- Decide the bindless binding model unilaterally — it is a joint decision with Phase 5, and
  getting it wrong wastes weeks there.
- Apply Y-inversion in both the shader compiler and the Vulkan viewport.
- Vendor SPIRV-Reflect into `Code/**/ThirdParty/`.
