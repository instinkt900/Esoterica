# Building and Running on Linux

How to take a clone to a running editor. [Progress.md](Progress.md) records *what was found* and
*what is in flight*; this document is the standing recipe. When the two disagree, Progress.md is
newer.

The other documents cover the port's rules and design. This one assumes you only want to build
it and run it.

---

## The three things that catch everyone

Each of these produces an error that names something other than its cause. They are listed first
because knowing them makes the rest of this document unnecessary.

1. **`External/LLVM/bin` must be on `PATH`.** The port does not use a distribution clang.
   `Toolchain.py` writes a bare `clang++` into the ninja file, so without this you get
   `FileNotFoundError: [Errno 2] No such file or directory: 'clang++'` from `NinjaGen.py`.
2. **The Resource Server is a separate target.** Building the editor does not build it. Without
   it the editor spawns nothing and repeats
   `Unable to connect to 127.0.0.1 on port 5556 ... Connection refused` until you close it.
3. **`Build/Linux_<configuration>/Esoterica.ini` is untracked and hand written.** It needs a
   `[Resource]` section naming the Linux executables. The defaults are
   `EsotericaResourceServer.exe` and `EsotericaResourceCompiler.exe`, which do not exist here.

## Prerequisites

Run `./DownloadDependencies.sh` first. It builds and installs everything under `External/`,
including the pinned LLVM and SDL3.

**Packages to install first.** The script names everything it checks for in one message, so most
of these produce a clear failure rather than a nested CMake one. Three it cannot check, and they
are the three worth installing before you start:

```bash
sudo apt install libsqlite3-dev protobuf-compiler libprotobuf-dev \
                 libxss-dev libxtst-dev vulkan-tools vulkan-validationlayers rustup
```

- `libsqlite3-dev` - **not checked, and it fails late.**
  `EngineTools/Resource/ResourceCompilationDatabase.cpp` includes `sqlite3.h`, so it is the
  engine build that needs it. The dependency script only ever builds `External/` and never sees
  it.
- `vulkan-tools` and `vulkan-validationlayers` - **not checked, because neither is a build
  dependency.** `vulkaninfo` is a diagnostic, and host validation silently does nothing without
  the layers. [Progress.md](Progress.md)'s run recipe turns validation on and needs them.
- `rustup` - checked, both that `cargo` exists and that it is 1.90 or newer. Listed anyway
  because the package **removes** `rustc` and `cargo`: Ubuntu 24.04 ships Rust 1.75 and `ctt`
  needs 1.90. Run `rustup default stable` afterwards.
- `libxss-dev` and `libxtst-dev` - checked. SDL3's `CheckX11` stops at the first missing
  extension, so before they were checked each one cost its own CMake run to discover.
- `protobuf-compiler` and `libprotobuf-dev` - checked. See the note below.

**A stale `protoc` earlier on `PATH` is harmless.** It used to break GameNetworkingSockets:
CMake's `FindProtobuf` takes the library from the standard prefix but `protoc` from `PATH`, so a
3.17.3 in `~/bin` shadowing the system 3.21.12 generated `.pb.h` files against headers they did
not match, and the build failed with "generated by an older version of protoc". The script now
asks `pkg-config` for the compiler in the same install prefix as the library and passes it to
CMake, so **the old `PATH=/usr/bin:$PATH` workaround is no longer needed**. It prints which
`protoc` it used whenever that is not the one on `PATH`.

**Use an X11 session, not Wayland.** `ImGui_ImplSDL3_Init` only sets
`ImGuiBackendFlags_PlatformHasViewports` for video drivers on its global-mouse white list, and
`wayland` is not on it. The editor's docking UI needs viewports. Check with
`echo $XDG_SESSION_TYPE`.

## The toolchain

`External/LLVM/bin` holds clang 21.1.8, `ld.lld` and `llvm-ar`. The version matters: it is the
LLVM the Reflector links against, and clang's C++ AST API is not stable across major versions.

Prepend it for every `NinjaGen.py` and `ninja` invocation:

```bash
export PATH="$PWD/External/LLVM/bin:$PATH"
```

The rest of this document assumes you have done that.

## Targets

All eleven come out of `Build/Linux/Esoterica.ninja`. The paths below use `Release`; see
[Configurations](#configurations) for how to ask for another one, and for the two that do not
have all eleven.

| Target | What it is |
|---|---|
| `Build/Linux_Release/Esoterica.Applications.Reflector` | Reflection and shader codegen. Build this first |
| `Build/Linux_Release/Esoterica.Applications.ResourceCompiler` | Compiles one resource, also runs as a server worker |
| `Build/Linux_Release/Esoterica.Applications.ResourceServer` | Serves resources on `127.0.0.1:5556`, spawns workers, has a UI |
| `Build/Linux_Release/Esoterica.Applications.Engine` | The runtime. Takes `-map data://<path>` |
| `Build/Linux_Release/Esoterica.Applications.Editor` | The editor |
| `Build/Linux_Release/Esoterica.Applications.Tester` | Test harness |
| `libEsoterica.Base.so` | Shared libraries. Built as dependencies, rarely by name |
| `libEsoterica.Engine.Runtime.so` | |
| `libEsoterica.Engine.Tools.so` | |
| `libEsoterica.Game.Runtime.so` | |
| `libEsoterica.Game.Tools.so` | |

`Esoterica.Applications.BuildGenerator` is Windows-only. `NinjaGen.py` reports it as eight
problems, one per configuration, and that is expected output rather than a failure.

## Configurations

**Nine configurations, one ninja file, and the configuration *is* the output path.** There is no
per-configuration generate step, no `--config` flag on `NinjaGen.py` and no second ninja file:
`Build/Linux/Esoterica.ninja` carries every rule for all nine, and you pick one by naming the
target you want.

```bash
ninja -f Build/Linux/Esoterica.ninja Build/Linux_Debug/Esoterica.Applications.Editor
#                                                ^^^^^ the whole selector
```

| Configuration | Output directory | Notes |
|---|---|---|
| `Debug` | `Build/Linux_Debug/` | Asserts on, no optimisation. **`EE_DEBUG` forces host validation on** whatever the ini says (`RenderSystem.cpp:36`), here and in the three `Debug_*` sanitizers |
| `Release` | `Build/Linux_Release/` | **Prefer this.** The port's verified state is all in `Release`, and Debug is a cold build of the whole tree |
| `Shipping` | `Build/Linux_Shipping/` | `-flto`, and **only four targets exist** - see below |
| `Debug_ASan` `Debug_TSan` `Debug_UBSan` | `Build/Linux_Debug_<Sanitizer>/` | |
| `Release_ASan` `Release_TSan` `Release_UBSan` | `Build/Linux_Release_<Sanitizer>/` | The three P8.6 built and ran. See [the sanitizer configurations](#the-sanitizer-configurations) - two need a runtime option or they look like engine bugs |

**All nine build**, as of P8.6 on 2026-09-03, and the engine has been run in `Debug`, `Release`,
`Shipping` and the three Release sanitizers.

### Four things about configurations that are not obvious

**1. `ninja` with no target named builds every `Debug` target, not `Release`.** `NinjaGen.py`
writes `Debug` into the `default` rule and nothing else, so the bare command in
[AGENTS.md](../../AGENTS.md#definition-of-done) is a Debug build:

```bash
ninja -f Build/Linux/Esoterica.ninja                      # every Debug target
ninja -f Build/Linux/Esoterica.ninja Build/Linux_Release/Esoterica.Applications.Editor
```

**A green bare `ninja` therefore says nothing about `Release`,** and a Release binary can sit a day
stale behind one. Name the target whenever you mean a configuration.

**2. The Reflector is always built in `Release`, whichever configuration you want.**
`RunReflection.sh` and `CompileShaders.sh` both hardcode
`Build/Linux_Release/Esoterica.Applications.Reflector` and exit with an error naming it if it is
missing. So step 1 of the recipe below is `Release` even for a Debug-only build. **What they
generate is configuration-independent** - reflection and shader code lands in
`Code/**/_Module/_AutoGenerated/` and is compiled into every configuration - so steps 1 to 3 are
done once, not once per configuration.

**3. `Shipping` builds four targets, not eleven.** `Esoterica.Applications.Engine`, and static
`libEsoterica.{Base,Engine.Runtime,Game.Runtime}.a`. There is no Shipping editor, Resource Server,
Resource Compiler, Reflector or Tester, and the libraries are `.a` rather than `.so` because
`Esoterica.props` sets `EE_DLL` for Debug and Release only. Asking ninja for a Shipping editor gets
`unknown target`, and that is the generator agreeing with the solution rather than a gap.

**4. Each configuration directory needs its own `Esoterica.ini` and its own data.** Both are
untracked and neither is inherited, so switching configuration is not free - a fresh directory
starts with `Couldn't start resource server`. See [The `Esoterica.ini` file](#the-esotericaini-file)
for what to write, and the [sanitizer section](#the-sanitizer-configurations) for the two-line trick
that borrows the `Release` build's compiled data instead of recompiling it.

## Building from a clone

The order matters. Reflection generates C++ that the build compiles, so it sits in the middle of
the build rather than before it.

```bash
export PATH="$PWD/External/LLVM/bin:$PATH"

# The configuration you want. Debug, Release, Shipping, or one of the six
# sanitizer configurations - see Configurations above.
CONFIG=Release

# 1. Generate the ninja file, then build the Reflector. Release, always:
#    RunReflection.sh and CompileShaders.sh hardcode that path.
python3 Code/Scripts/NinjaGen/NinjaGen.py
ninja -f Build/Linux/Esoterica.ninja Build/Linux_Release/Esoterica.Applications.Reflector

# 2. Generate reflection and shaders. Configuration-independent; run once.
./RunReflection.sh
./CompileShaders.sh

# 3. Re-run NinjaGen. The generated .cpp files are found by a glob, so the
#    build cannot see them until the ninja file is rewritten.
python3 Code/Scripts/NinjaGen/NinjaGen.py

# 4. Build what you want, in the configuration you want.
ninja -f Build/Linux/Esoterica.ninja \
  Build/Linux_${CONFIG}/Esoterica.Applications.ResourceServer \
  Build/Linux_${CONFIG}/Esoterica.Applications.ResourceCompiler \
  Build/Linux_${CONFIG}/Esoterica.Applications.Editor
```

**Only step 4 is per-configuration.** Steps 1 to 3 are done once for the clone: a second
configuration is step 4 again with a different `CONFIG`, plus that directory's own
`Esoterica.ini`. For `Shipping`, step 4 is `Build/Linux_Shipping/Esoterica.Applications.Engine`
alone - the other three targets do not exist there.

**Re-run `CompileShaders.sh` and then `NinjaGen.py` after any shader change, including one that
arrives in a merge.** Nothing warns you. `ninja` does not know the `.esh` and `.esf` sources, so
the build stays green while the binary carries the old SPIR-V. The symptom is a
`vkCreateShaderModule` validation error naming a capability the device lacks, which reads
exactly like a hardware gap. Check the dates before believing it:

```bash
ls -l Code/Engine/_Module/_AutoGenerated/Shaders/ShaderRegistration.cpp Code/Base/Render/RHI.esh
```

**The build is warning-free, and it takes three warning policies to be.** `Toolchain.py` picks one
per source file, by who owns the file:

| Tier | Sources | Policy |
|---|---|---|
| Fork | The 18 compiled sources in `LinuxSources.txt` | `-Wall -Wextra -Werror`, minus the Vulkan partial-initialiser idiom and `-Wunused-parameter` |
| Upstream | Everything from a `.vcxproj` | `-Wall -Wextra`, minus a list of 32 flags upstream trips |
| Generated | `_Module/_AutoGenerated/` | `-w` |

**New code in a fork-owned file fails the build on a warning.** That is the point of the split: the
32-flag list exists so that upstream's warnings do not drown out this fork's, and upstream's are not
this fork's to fix (Conventions rule 3). Third-party and `External/` include paths are passed with
`-isystem` rather than `-I`, so clang does not report their headers at all.

Re-check it after a merge, or when a new upstream warning class appears:

```bash
python3 Docs/Linux/Scripts/WarningSweep.py               # every TU, attributed by owner
python3 Docs/Linux/Scripts/WarningSweep.py --audit-fork  # what the fork tier suppresses
```

It exits non-zero if anything warns. `--audit-fork` reports exactly 106 sites, all of them
`VkFooCreateInfo x = { VK_STRUCTURE_TYPE_FOO }` in `RHI_Vulkan.cpp`; that idiom has no warning-free
spelling, and the reasoning is on `Toolchain.FORK_WARNING_FLAGS`.

## The `Esoterica.ini` file

`Build/Linux_<configuration>/Esoterica.ini` is untracked, so each configuration directory needs
its own. `Settings::SaveSettings` omits every property still at its default, so a generated file
is empty and the sections have to be written by hand.

```ini
[Resource]
Resource_Server_Exe_Name = Esoterica.Applications.ResourceServer
Resource_Compiler_Exe_Name = Esoterica.Applications.ResourceCompiler

[Render:RHI]
Enable_Host_Validation = true
```

Key names are the reflected `Category` and `FriendlyName`, with spaces replaced by underscores,
which is what `Settings::GenerateSectionAndKeyIDs` builds.

**The `[Resource]` keys are required.** Without them the editor and the engine look for
`EsotericaResourceServer.exe` and report `Couldn't start resource server`.

**Host validation is off unless the ini turns it on.** `RenderSettings::m_enableHostValidation`
defaults to false, and only a Debug build forces it on. That is upstream behaviour, not a Linux
defect.

## Running

Every command below uses `Build/Linux_Release`. Substitute the directory of whatever you built;
the binaries take the same arguments in every configuration. A binary only runs from its own
directory - the rpath is `$ORIGIN` relative, and the ini and compiled data live beside it.

### The editor

```bash
cd Build/Linux_Release
./Esoterica.Applications.Editor
```

It starts the Resource Server itself, through `EnsureResourceServerIsRunning` in
`Code/Base/_Module/BaseModule.cpp`. You do not need to start it by hand.

**A few `Connection refused` errors in the first second are normal.** The editor spawns the
server and connects before it has bound the port, so the first attempts fail and the retry
succeeds. Confirm with:

```bash
ss -ltnp | grep 5556
```

A `LISTEN` line means the server is up, with its worker processes sharing the socket. Errors
that continue past the first second or two are the real thing; see the table below.

### The engine

```bash
cd Build/Linux_Release
VK_KHRONOS_VALIDATION_DEBUG_DISABLE_SPIRV_VAL=true \
  ./Esoterica.Applications.Engine -map data://demo/render/pbr/pbrdemo.map
```

`-packaged` is no longer required. It still works, and reads
`Build/Linux_<configuration>/CompiledData` directly instead of going over the network.

`VK_KHRONOS_VALIDATION_DEBUG_DISABLE_SPIRV_VAL=true` disables only the validation layer's
bundled spirv-val, where a stale SPIRV-Tools lives, and leaves every other check on. Do not
reach for `VK_LOADER_LAYERS_DISABLE='*'`, which turns off validation entirely.
`VK_LAYER_MESSAGE_ID_FILTER=<vuid>[,<vuid>]` silences one VUID at a time.

### The Resource Server on its own

```bash
cd Build/Linux_Release
./Esoterica.Applications.ResourceServer
```

It has a full UI showing connected clients and the request table. Useful when you want to watch
what the editor asks for. Only one can run: a second fails to bind 5556 and says
`Cant open network connection on port: 5556`.

### Stopping everything

There is no `KillEsotericaProcesses.sh`; only the `.bat` exists.

```bash
pkill -f "Esoterica.Applications"
```

Worth running after a crash. Anything left holding 5556 makes the next launch look like a
networking failure.

**The server is not the only thing that can hold the port.** Its `ResourceCompiler -worker`
children inherit the listening socket, and they can outlive it: after one editor session the
server was gone while two workers were still `LISTEN`ing on 5556, reparented to `init`. A
Resource Server started after that cannot bind, so the symptom is a networking error with no
server anywhere in `ps`. The `pkill` above matches the workers too, which is why it is worth
running even when no server appears to be up.

### The sanitizer configurations

All six generate, and P8.6 built and ran the three Release ones. Substitute the sanitizer name:

```bash
ninja -f Build/Linux/Esoterica.ninja Build/Linux_Release_ASan/Esoterica.Applications.Engine
```

An output directory needs the same hand-written `Esoterica.ini` as any other, and the quickest way
to give it data is to borrow the Release build's:

```bash
cp Build/Linux_Release/Esoterica.ini Build/Linux_Release_ASan/
ln -sfn ../Linux_Release/CompiledData Build/Linux_Release_ASan/CompiledData
cd Build/Linux_Release_ASan
./Esoterica.Applications.Engine -packaged -map data://demo/render/pbr/pbrdemo.map
```

`-packaged` reads that `CompiledData` directly, so no Resource Server is needed. That matters
here: the server would have to be a binary built with the same sanitizer, because an executable
that loads an ASan-instrumented `.so` without being instrumented itself refuses to start.

**ASan needs `protect_shadow_gap=0`, or Vulkan will not start.**

```bash
ASAN_OPTIONS=detect_leaks=1:protect_shadow_gap=0 ./Esoterica.Applications.Engine ...
```

The NVIDIA driver maps memory inside the region ASan reserves as its shadow gap. Without the
option `vkCreateDevice` fails and the engine halts on `EE_ASSERT( result == VK_SUCCESS )` at
`RHI_Vulkan.cpp:1288` - **a symptom that names Vulkan for a cause that is the sanitizer.**

**ASan cannot see engine allocations.** `Memory.h:13` hardcodes `EE_USE_CUSTOM_ALLOCATOR` to 1, so
everything comes from rpmalloc, which takes its memory from `mmap`. What ASan covers is the stack,
globals and libc-level heap. Turning rpmalloc off does not compile on Linux; see
[Progress.md, Still open](Progress.md#still-open).

**TSan cannot run against the NVIDIA driver at all.** It fails inside its own interceptors right
after `vkCreateDevice`:

```
ThreadSanitizer: CHECK failed: tsan_interceptors_posix.cpp:2156 "((thr->slot)) != (0)"
```

No `TSAN_OPTIONS` setting tried avoids it. Two ways round it, both proven:

```bash
# Mesa's software ICD. The engine reaches the render path, but lavapipe has no VK_EXT_mesh_shader,
# so the frame halts the way any device without it does.
VK_ICD_FILENAMES=/usr/share/vulkan/icd.d/lvp_icd.json ./Esoterica.Applications.Engine -packaged -map ...

# The resource compiler. Threaded, and touches no Vulkan.
./Esoterica.Applications.ResourceCompiler -compile data://demo/render/pbr/boulder/boulder.mesh -force
```

## Troubleshooting

| Symptom | Cause |
|---|---|
| `FileNotFoundError: ... 'clang++'` from `NinjaGen.py` | `External/LLVM/bin` is not on `PATH` |
| `Connection refused` on `127.0.0.1:5556`, continuously | The Resource Server target was never built |
| `Couldn't start resource server (.../EsotericaResourceServer.exe)` | The `[Resource]` keys are missing from `Esoterica.ini` |
| `Cant open network connection on port: 5556` | A Resource Server is already running, **or orphaned `ResourceCompiler -worker` processes still hold the inherited socket with no server running**. `pkill -f "Esoterica.Applications"` |
| `NinjaGen.py` reports 8 `BuildGenerator` problems | Expected. It is a Windows-only application |
| A green `ninja` run, and the binary you were testing is still stale | The bare command builds **`Debug` only**. `default` lists the Debug targets and nothing else. Name the target |
| `ninja: unknown target 'Build/Linux_Shipping/Esoterica.Applications.Editor'` | Shipping builds the engine and three static libraries. There is no Shipping editor, server, compiler, Reflector or tester |
| `RunReflection.sh` or `CompileShaders.sh`: `Build/Linux_Release/Esoterica.Applications.Reflector does not exist` | Both hardcode the **`Release`** Reflector, whichever configuration you are building. Build that target first |
| `vkCreateShaderModule` rejects a capability the device has | Stale SPIR-V. Re-run `CompileShaders.sh`, then `NinjaGen.py` |
| Editor UI does not undock into separate windows | A Wayland session. Log into X11 |
| `error while loading shared libraries` | Running a binary moved out of `Build/Linux_<configuration>/`. The rpath is `$ORIGIN` relative |
| ASan build: `vkCreateDevice` fails, then `EE_ASSERT( result == VK_SUCCESS )` | Missing `ASAN_OPTIONS=protect_shadow_gap=0`. The NVIDIA driver maps into ASan's shadow gap |
| TSan build: `CHECK failed: tsan_interceptors_posix.cpp` after device creation | TSan cannot run against the NVIDIA driver. Use the lavapipe ICD or the resource compiler |
| ResourceCompiler exits 1 after compiling successfully | Upstream behaviour. Count `"Compiled successfully"` in its log, not the exit code |

## What this document does not cover

- **Windows.** Use `Esoterica.slnx` and the steps in the root [README.md](../../README.md).
  **Debug was built and run there on 2026-09-04** - Reflector, shaders, Resource Server and the
  editor rendering pbrdemo - so the port does not break the Windows build. What is still unbuilt
  there, and the two comparisons nobody has run, are the Windows queue in [Blocked.md](Blocked.md).
- **Packaging or shipping a build.** The `Shipping` configuration builds; nothing beyond that
  has been exercised.
- **Rendering gaps by device.** [Progress.md](Progress.md) has the hardware table and the
  current state of the frame.
